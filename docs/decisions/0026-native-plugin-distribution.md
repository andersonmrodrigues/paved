# 0026. Native plugin distribution and explicit runtime upgrade

- **Status:** Accepted
- **Date:** 2026-09-28
- **Extends:** [0024](0024-agent-integration-projections.md), [0025](0025-packaged-runtime-and-workflow-execution.md)
- **Amended by:** [0032](0032-update-adopts-newer-plugin-runtime.md) (`update` adopts a newer plugin runtime), [0034](0034-unpacked-plugin-runtime.md) (the runtime ships unpacked)

## Context

The packaged runtime and its launcher worked from a local tarball, but a consumer had
no supported way to obtain them: `paved-core` is not on npm and the project-local
projections had to be generated from a Core checkout. Codex and Claude Code both
install plugins natively from a Git repository that carries a marketplace file.
ADR 0025 also left runtime version changes and legacy-lock migration without a
validated transaction.

## Decision

- This repository is its own marketplace. `.agents/plugins/marketplace.json` (Codex)
  and `.claude-plugin/marketplace.json` (Claude Code) list one plugin, `paved`, at
  `plugins/paved/`.
- `plugins/paved/` is generated by `npm run build:plugin` from
  `plugins/plugin-source.json`, the canonical skill catalog, the shared command
  catalog and `integrations/shared/bootstrap.mjs`, and is committed. It carries a
  portable `plugin.json`, both host manifests, one skill per canonical skill and per
  command, the launcher, and the `paved-core` runtime packed from this repository
  with its dependencies bundled. `provenance.json` records every file digest; the
  build refuses to overwrite hand-edited files and the tests fail on drift.
- Commands are skills, not a separate commands directory, so each name registers
  once: `/paved:<name>` in Claude Code and `paved:<name>` in Codex.
- The launcher resolves the consumer (explicit `--project`, else the nearest
  directory with `.paved/manifest.yaml` or `.git`), passes it to the runtime
  explicitly, and refuses the plugin directory and the Core checkout.
- The lock stays authoritative. A plugin carrying another runtime only reports it.
  `runtime upgrade` verifies and activates the plugin runtime, which then moves the
  lock through the Core's transactional update; on failure the previous selection
  is restored and the lock is untouched. The previous lock bytes and selection are
  kept for `runtime rollback`. The same path adopts a legacy lock without a runtime.

## Consequences

- Consumers install with the agents' own commands and activate the runtime offline;
  no npm publication, global install or application dependency is needed.
- The repository carries a generated runtime tarball (under 1 MB) that must be
  rebuilt with every Core change the plugin projects.
- Publication to public plugin directories and to npm remains a separate step.

## Alternatives considered

- **Registry-only runtime.** Rejected: it needs an npm release and network on first
  use, and still leaves the plugin without a verifiable artifact.
- **Separate `commands/` directory.** Rejected: Claude Code would register command and
  skill names twice, and Codex does not read it.
- **Silent runtime replacement on plugin update.** Rejected: it would change a
  committed lock without review and without rollback.
- **Downloading the runtime from GitHub releases at first run.** Rejected: it adds a
  network dependency and a second trust root for no benefit over the committed
  artifact.
